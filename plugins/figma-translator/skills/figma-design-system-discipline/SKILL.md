# デザインシステムを崩さずに育てる

部品と台帳が増えても壊れない作りにするための作法。**どれも「あとで効いてくる」もの**で、
その場では守らなくても動くが、守らなかった分だけ後で誰かが読み違える。

---

## 1. 台帳は写さない。読む

**人に見せる一覧を、手で書き写して持たない。**

- トークンの一覧 → **台帳のファイルをその場で読んで並べる**（CSS を `?raw` で読んでパースする等）
- 部品の一覧 → **ソースの先頭コメントから作る**（`// Figma: …（NNN:NNNNN）`）

写した一覧は、**台帳を直した日から古くなる。しかもそれは見た目に出ない** —— 一覧は「載っている」という
同じ顔のまま、違う値を出す。

**読めなかった行・分類できなかったもの・登録先が見つからないものは、黙って捨てずに面へ出す**（fail-closed）。
「0件」と表示されることが、網が破れていないことの証明になる。

---

## 2. 同じ見た目を2箇所に書かない

同じ意味のものが面ごとに違う形にならないよう、**部品は1つに寄せる**。
面のローカルに同じ見た目を書き起こすと、片方だけ直された瞬間に**2通りの正解**ができる。

**似た症状が3度出たら、それは面の問題ではなく部品が無いという意味に取る。**

同じことは**器**にも当てはまる。角丸・影・切り抜きのような「その部品らしさ」を面ごとに手で組むと、
丸めた面と丸め忘れた面が並ぶ。**器を1部品に寄せ、面が意匠を決められないようにする。**

---

## 3. 省略できない prop（既定値を持たせない）

面が決めるべき軸には、**既定値を与えない**。

```tsx
<EmptyStatus type="card" label="…" />          // どの器に置く空状態かを必ず言う
<FormField necessity={Necessity.Optional} … />  // 必須か任意かを必ず言う
<StatusTag status={Status.Waiting} />           // 誰の番かを必ず言う
```

既定があると、**書き忘れた面が黙って片方の姿で描かれる**。それは「間違って描かれた」ではなく
「何も言っていないのに、何かを言ってしまった」状態で、レビューでも気づけない。

---

## 4. 境界の拡張は、消費側とセットで

列挙に値を1つ足したら、**それを使う側が埋まるまでビルドが通らない**形にする。

```ts
const LABEL: Record<Status, string> = { … }          // 足すと型が落ちる
switch (kind) { … default: { const _: never = kind } } // 書き忘れが型で出る
```

`satisfies` は片方向しか保証しない。台帳側の追加も落としたいなら、**双方向の包含チェック**を足す。
テストがあるなら、**列挙を回して全ケースを検証**する（配列を手で並べない）。

---

## 5. 表示用の文字列を、機械が読む前提にしない

**「週3回（月・水・金）」「45Lポリ袋×4袋 目安」のような文は、人が読むためのものである。**
そこから曜日や数量を機械が取り出す作りにすると、**言い方を変えた瞬間に壊れる**。しかも壊れ方が静かで、
画面は「そういうものだ」という顔のまま違うことを言う。

**構造をモデルに持たせ、表示用の文字列はそこから導く。**
入力側の型で「構造を持つときは文を手で書けない」ようにできるとなおよい。

同じ轍を二度踏みやすいので、**データを足すときに毎回問う**:
> これは人が読む文か、機械が読む値か。両方なら、どちらが出どころか。

---

## 6. 区別に使えない情報は置かない

**全部の行に同じ札が並ぶなら、その札は何も言っていない。**

- 同じ状態のものだけが並ぶページに、その状態のタグを出さない
- 親がひとつしか無い面に、親の名前を出さない
- 逆に、**行ごとに違うものは出す**（同じ規律の裏側）

「この面の読み手は、この情報で何を決めるのか」を問う。決めるのに使わない情報は、
**別の面が持っている**（そこで読めばよい）。

---

## 7. 色は「性質」で棚を分ける

1つの棚に性質の違うものを混ぜると、**1系統がいくつもの意味を運ぶ**ようになる。

| 棚 | 何を置くか | トーンの深さ |
|---|---|---|
| **状態** | 時間とともに変わるもの（あなたの番 / 相手の番 / 成った / 断った / もう動かない） | 全トーン。押せるものは Hover / Down も |
| **分類** | 変わらない属性（種別・区分） | 地と文字だけ（**押されないので Hover / Down を持たない**） |
| **区別だけ** | 意味を持たない印（グラフの系列・列グループ） | 図に要るぶん |
| **話者・固有** | 誰の声か（自分 / 相手 / AI） | 面が要るぶん |

**1系統＝1つの意味**に絞る。「あなたの番です」の色が「予定」や「話者」も兼ねていたら、
その色はもう手番を言っていない。

**意味を持たない色に、意味のある色を借りない。** グラフの系列に「成功」の緑を使うと、
読む人は「緑の系列＝好調」と読む。系列の色は隣と違うことしか言っていないのに。

**意味が無いなら、無いと書く。**
> この緑に意味はない。よくあるチャットアプリの慣習に合わせているだけである。

と書いておかないと、次に読む人が「自分の発言は成功なのか」と意味を探す。

### 色を実際に選ぶときの落とし穴

- **同じ明度でも、黄や緑は知覚上ずっと明るい。** 全色相を同じ明度に置くと、そこだけ蛍光色に見える。
  濃い段は**明度ではなく白地に対する重さ**で揃えるか、その色相だけ彩度を落とす
- **くすませて他と分ける手は、同じ図の中では裏目に出る。** 系列だけ沈んで読みにくくなる
- **彩度を上げると、色相の小さな差は消える。** 8° 差の2色は、くすんでいれば見分けられても、
  彩度を上げた瞬間に同じ色になる。**同じ register の中では色相の差だけが分ける**
- 台帳の値を**面から上書きしない**（部品が持っている余白・色を面が塗り替えない）

---

## 8. 黙って失敗させない

- **分からない入力は既定へ倒さず、はっきり拒む。** 「読めなかった」と「正しく既定を指していた」を
  区別できる形にする（解く関数は null を返し、既定へ倒すのは呼ぶ側）
- **外から来た文字列で台帳を引くときは `Object.hasOwn`**（`in` は `constructor` のような
  受け継いだ名前にも当たる）
- **空の状態は空白にせず、何が無いのかを名指しする**
- **押せるのに何も起きないボタン**や、**URL に書けるのに開かない画面**を作らない

---

## 9. 計算で作られる面には、検算を置く

**計算違いは画面を壊さない。**「そういうものなのだろう」と読めてしまう。
月のかたち、合算した数量、往復する URL —— **見た目が正しそうに見えるもの**ほど危ない。

小さな検算スクリプトを1本置き、**全数**を回す（サンプルではなく）。
壊し方を仕込んで、**実際に落ちること**まで確かめる。

---

## 10. ハードカットオーバー（後方互換を残さない）

古い綴り・古い概念を**同じウェーブで消す**。「移行中は両方サポート」と書いた瞬間が、移行を終える時である。

**grep が真実**であって、「触ったファイルは全部直した」という記憶ではない。
退役した綴りを**全層**（ソース / テスト / docs / 設定 / データ / SVG）に当て、ヒットを1つずつ分類する。

**動的に組まれるトークン名に注意**:
```ts
`var(--color-${shelf}-${kind}-base-lv${level})`   // 静的 grep で見つからない
```
改名の前に、**動的に組んでいる箇所を先に洗い出す**。

---

## 11. 「なぜこの設計か」をコードに残す

コメントに書くのは**何をしているか**ではなく、**なぜそうしたか**と**そうしなかった案**。

```ts
// **なぜ枠ではなく塗りか**: セルの中に小さなカードが複数並ぶ面なので、枠だと線が何本も交差して、
// どこまでが1件かを目が拾い直すことになる。塊ごと塗れば、1件のかたまりが色の面として一度に読める。
```

**判断が変わったら、古い理由を消す。** 理由と実装が食い違ったまま残ると、次に読む人はどちらが
正しいのか判断できず、たいてい**古い理由のほうを信じる**。

---

## 12. 実機で「見た」と言えるまで確かめる

- **computed style で実測する**（目視だけで済ませない）。幅・色・余白は数で確かめる
- **見られなかったなら、見られなかったと書く**（「確認した」と書かない）
- ブラウザ自動化では、**タブが背面だとレイアウトが走らない**ことがある（寸法が 0 になる）。
  その状態の測定値を根拠にしない

---

## 13. 面の言葉は、読む人の言葉で

| 読む人 | どこ | 語り口 |
|---|---|---|
| 非エンジニア（実際の利用者） | 画面の文言 | **そのものの言葉**。比喩・開発用語・内部語彙を出さない |
| エンジニア（現在と未来の実装者） | README / コメント / docs | **技術用語はそのまま**（`fail-closed` / `middleware` を言い換えない） |

画面の平易さの規律を、**開発者向けの文書へ持ち込まない**。`password` を「合言葉」と言い換えるのは
親切ではなく、読み手に翻訳を強い、grep を壊す。

### 丁寧さは一段だけ

サービスの文面では、**敬語を重ねない**。

```
お決めください  →  判断してください
お選びください  →  選んでください
お探しして      →  探して
```

**丁寧さそのものは保つ**（やめるのは重ね掛け）。ぶっきらぼうにするのは別の失敗である。

**同じ行為は同じ言葉で言う。** 1つの行為が場面によって「打診する / 確認する / 伝える / 当たる」と
言い換わっていると、読む人は別のことが起きたと思う。**製品が既に使っている言葉に寄せる**（新しい言い方を作らない）。

手順: **同じ行為に何通りの言い方があるかを全数で洗い出し**、1つに決めてから直す。

### 問いと答えは噛み合わせる

```
✗  ◯◯に変わりはありますか？        ［はい］［修正する］   ← 「はい」＝変わった、になる
○  ◯◯はこの内容で合っていますか？   ［はい］［修正する］
```

**肢を先に決めたら、問いのほうを合わせる。**

---

## 14. 出力には根拠を持たせる（AI が話す面がある場合）

AI が画面に出す言葉は、次のどれかに根拠がなければならない。

1. **その人がその場で入力・選択したこと**
2. **登録情報から取れること**
3. **確度高く推測できること**（推測だと分かる言い方か、根拠が画面に出ている）

どれにも当たらないものは**作り話**である。先に聞く拍を足すか、根拠のある言い方に直すか、出すのをやめる。

**現状を前提にした問いには、その現状を出す。**
「変わりはありますか？」と聞くなら、**いまの内容を並べて見せる**。見に行かないと思い出せないものを
思い出せないまま「はい」を押させるのは、確認したことにならない。

物差しは1つ: **その問いに答えるために、読む人が画面の別の場所を見に行く必要があるか。**
